# Contributing to SmaLLM

Issues and pull requests are welcome. This page covers the AI policy, how to
build and test, where things live, and the rules every change is held to.

## AI policy

I am open to AI and agentic coding, but the code written needs to follow
specific guidelines:

1. MUST be human readable, acceptable variable/function names.
2. Easily traceable, following a good program flow.
3. Contributors MUST look at and document code and code changes. You need to
   understand the code that is being written.

## Build and test

SmaLLM needs Rust 1.85 or newer and nothing else.

```sh
cargo build --release                 # the smallm program, in target/release
cargo build --release -p smallm-capi  # the C library, in target/release
cargo test --workspace                # every test
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

CI runs all of these on Linux, macOS and Windows, on x86-64 and ARM. It also
runs the tests for 32-bit ARM and RISC-V under emulation, and checks that
the oldest supported Rust still builds everything without warnings.

### Tests that need model files

The golden tests compare SmaLLM with llama.cpp on real models. Model files
are not in the repository. Point `SMALLM_TEST_MODELS` at a folder that holds
them and the tests run. Models that are missing are skipped.

```sh
SMALLM_TEST_MODELS=~/models cargo test --release --test golden
```

`tests/golden.rs` lists the models. CI downloads the three smallest ones.
The C API and the Python binding have tests of their own that use the same
folder.
[tools/reference](tools/reference/README.md) explains how the golden files
are made.

### Measuring speed

```sh
smallm bench model.gguf             # prompt and generation speed
smallm bench model.gguf --profile   # where generation time goes, by stage
cargo test --release --lib kernel_speed -- --ignored --nocapture
```

The last command times each row kernel on a matrix that stays in the CPU
cache. Use it when you change a kernel.

## Common changes

| To | Edit |
|---|---|
| support a new architecture | `ARCHITECTURES` and the `match` in `model/config.rs`, which sets the model-wide switches and each layer's `LayerSpec`. New tensors go in `model/weights.rs`, new math in `model/forward.rs` and the oracle in `model/tests.rs`. Check it with `tests/compare.rs` and add a golden file from a real model |
| support a new weight format | `TensorType` in `tensor/mod.rs`, a decoder in `tensor/quant.rs`, and a row in `kernels/scalar.rs`. The scalar row is enough to be correct |
| speed up a weight format | a kernel in `kernels/x86.rs` or `kernels/arm.rs`. `kernels/tests.rs` checks it against the scalar one without further work |
| add a chat format | `Template` in `chat.rs`: detection, rendering and a test |
| add a word splitting rule | run `tools/gen_pretok.py` on a newer llama.cpp. A rule that is common and slow can get a scanner in `tokenizer/pretok.rs` |
| add a command | a file in `src/bin/smallm/commands/` and a line in `main.rs` |
| add an API endpoint | `route` in `src/bin/smallm/server/api.rs` |
| add a C function | `capi/src/lib.rs` and `capi/include/smallm.h`, together |

## Rules

1. **No dependencies.** The engine, the program and the C API use the Rust
   standard library only. A feature that needs a crate needs a discussion
   first.
2. **Small and fast come first.** Measure before and after a change to a hot
   path, and say what you measured in the pull request.
3. **Model files are untrusted input.** Parsing never panics and never reads
   out of bounds. Add a test with a broken file when you touch the reader.
4. **Unsafe code states its contract.** Every `unsafe` block has a `SAFETY`
   comment that says why it is sound.
5. **Comment the code.** Say what a function is for and why it is written
   the way it is. Describe formats and algorithms where they are implemented.
6. **Write plainly.** Short sentences, one idea each, in comments, docs and
   messages. No run-on sentences.
7. **American English.** Color, behavior, canceled, normalize.
8. **No em dashes and no middle dots as separators.** Use commas, periods,
   colons or parentheses. `tests/writing.rs` checks rules 7 and 8.
9. **Keep the map true.** A new file gets a line in the project map above.
10. **No AI attribution in git.** Commit messages and pull requests carry no
    `Co-Authored-By` trailer or "generated with" line for an AI tool.

## Commits and pull requests

- Branch from `main`, and keep a pull request to one change.
- A commit message says what changed in one short line, like
  "Add the Q4_1 kernel for NEON". Add a body when the reason is not obvious.
- CI must pass. A change to a kernel or the forward pass needs a test that
  fails without it.

## Releases

1. Set `version` in `Cargo.toml` and `capi/Cargo.toml`, and give the version
   a section in `CHANGELOG.md`.
2. Push to `main`, and wait for `ci` and `release` to pass. Every push runs
   the release build without publishing it.
3. Tag it: `git tag v0.1.0 && git push origin v0.1.0`.

The release workflow builds the program and the C library for every
platform, writes `SHA256SUMS`, and publishes them with the changelog section
as the notes. The installers download from the newest release.
